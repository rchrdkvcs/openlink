# Serve workspace domains through a Cloudflare edge

The hosted instance moves to a managed platform that routes only the hostnames registered on it and charges for each one. Registering every workspace domain on the platform would tie domain setup to its API and quotas. Openlink therefore keeps a fixed set of hostnames on the platform (the application host, the Default Domain and an Edge Origin) and serves workspace domains through a Domain Edge.

The Domain Edge is chosen with `OPENLINK_DOMAIN_EDGE`. `direct` keeps the self-hosted behaviour (ADR 0003): domains point at the instance's own reverse proxy and become active when their DNS resolves to the DNS Target. `cloudflare` uses Cloudflare for SaaS: workspace members add a single CNAME to the DNS Target, Openlink registers the domain as a custom hostname, and a Worker forwards the traffic to the Edge Origin. Any other value is a configuration error and stops the application instead of silently falling back to `direct`.

## Decisions

- **Provision on the first record, activate on ownership.** Openlink creates the custom hostname as soon as it finds either the TXT record from ADR 0001 or a CNAME pointing exactly at the DNS Target, so certificate issuance overlaps TXT propagation. Activation still requires the TXT record: every domain shares the same CNAME target, so a CNAME does not prove which workspace owns the domain.
- **Active means served.** With the Cloudflare edge, a domain becomes active when its TXT record is found and its custom hostname and certificate are both active, replacing the IP comparison. Observed traffic still activates an ownership-verified domain. Each check records the domain's edge status (`waiting`, `issuing`, `connected`), so the setup page can say that the CNAME was found and HTTPS is being issued, and Cloudflare's validation errors are translated into plain language.
- **HTTP certificate validation.** Custom hostnames use HTTP validation and TLS 1.2 or later, so the CNAME is the only routing record a member adds.
- **Derived Cloudflare settings.** The DNS Target is the zone's Cloudflare for SaaS fallback origin, read from the API and cached, and the instance settings show it as managed by Cloudflare. The zone is discovered from the API token when it can read exactly one zone; `OPENLINK_CLOUDFLARE_ZONE_ID` is only needed, and always wins, otherwise. `php artisan openlink:edge-check` verifies the whole setup so a misconfiguration fails loudly for the operator instead of leaving every member waiting.
- **Signed forwarding.** The Worker sends the visitor's host, IP address and country in `X-Openlink-*` headers with a shared secret. A global middleware applies them only when the secret matches one of `OPENLINK_EDGE_SECRET`, a comma-separated list so secrets can be rotated without downtime. On signed requests it discards every incoming `X-Forwarded-*` and `Forwarded` header before setting its own, so headers a visitor sends through the Worker can never be trusted, and it strips `X-Openlink-*` from every request. The rest of the application keeps reading the request host, IP address and `CF-IPCountry`. The secret is infrastructure configuration and stays in the environment (ADR 0002).
- **Direct means operator-routed.** The direct edge no longer treats Cloudflare proxy addresses as pointing: self-hosted instances route workspace domains through their own reverse proxy, and the setup page tells members that an administrator must add the domain there before it serves HTTPS. Observed traffic still activates domains behind proxies the IP check cannot see.
- **Durable release.** Every path that removes a domain from the edge releases its custom hostname: disabling, deleting (including through its workspace or its owner's account), turning it into the Default Domain, losing both records before activation, and staying inactive for 30 days after it was added. Abandoned domains are skipped by the scheduled checks but stay checkable from the setup page. Releases are queued after the database commit and retried with backoff; Cloudflare answering `404` counts as released, and a release that keeps failing is reported with the hostname to delete by hand.
- **Only a missing hostname is recreated.** When a stored custom hostname answers `404`, Openlink looks it up by name or creates it again. Refused (`401`, `403`), throttled (`429`) or failing calls leave it untouched and show the member a waiting reason; they are retried by the next check instead of failing the request. Domains whose certificate is being issued are rechecked every five minutes, others hourly.
- **Migrated domains stay active.** When an instance switches to the Cloudflare edge, `openlink:verify-pending-domains --all` provisions every domain and lists those that do not reach the edge, with their workspace and owner email. Those domains keep their `active` status and are flagged with **Update DNS** until their custom hostname is active, so existing links keep working wherever the old record still serves them.

## Considered options

- **Register every workspace domain on the hosting platform.** Rejected: it ties the product to one platform's API, per-domain pricing and limits, and asks members for platform-specific records.
- **Cloudflare Origin Rules to rewrite the host.** Rejected: host header overrides require an Enterprise plan, and the platform rejects unknown hosts.
- **A self-operated proxy with on-demand TLS.** Not chosen: it would support apex domains with a fixed IP address but adds a server to operate. Apex domains remain supported on the Cloudflare edge when the member's DNS provider offers CNAME flattening, `ALIAS` or `ANAME` records.
- **Provision only after the TXT record.** Rejected: members waited for TXT propagation and then again for certificate issuance. Provisioning on a matching CNAME costs at most a hostname that is released again when both records disappear or after 30 days.
