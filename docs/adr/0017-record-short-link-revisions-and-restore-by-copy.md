# Record Short Link revisions and restore by copying them forward

Every successful change to a Short Link's configuration appends one Link Revision inside the same database transaction as the change: a full snapshot of the restorable configuration after the change, a field-level before/after diff, the acting member, and the mutation channel (dashboard, API, or system). A rolled-back mutation therefore leaves no revision, and one logical mutation — however many rows it touches across the link, its tags, and its routing rules — produces exactly one revision. We chose full snapshots over storing only diffs so any revision can be previewed and restored on its own, without replaying the chain, and so the chain survives revisions written before a schema change.

Restoring never rewrites or deletes history. It copies the chosen snapshot forward through the same validation and write path as a normal edit, then appends a new `restored` revision that names its source. The restore must carry the revision number the member was looking at (`expected_revision`); the link row is locked and the number compared before anything is written, so a stale restore or edit is rejected instead of silently overwriting a newer change. Dashboard edits send the same check; API clients send it as `expected_revision` or as an `If-Match` ETag. Unconditional API writes stay accepted so existing clients keep working, with last-write-wins semantics.

**Consequences**

- Snapshots carry a schema version. A revision whose version the application no longer supports can still be read but cannot be restored, and says so.
- Restoration covers the Destination URL, Fallback URL, enabled and archived state, activation and expiration dates, Visit Limit, folder, tags, and ordered Smart Routing. It never changes the Short URL (domain and slug are shown in history but not restored), never resets successful visits or analytics, never rotates QR Code tokens, and never restores a visitor password: snapshots record only whether a link was protected.
- Referenced resources are resolved against the current workspace at restore time. A deleted folder leaves the link without a folder; deleted tags are recreated by name, as tag input already does; destinations and routing rules are revalidated against the current address.
- Routing rules and variants keep their identity when they still exist on the link with the same type, so analytics attributed to them stay connected. Restoring never deletes a rule or variant that analytics refer to: when the restored configuration leaves one out, it stays on the link turned off, after the restored rules, and the preview says so. Rules that are absent from the link are recreated as new rules. Only unreferenced rules and variants are deleted.
- Snapshots and diffs never hold query strings or fragments: every query value and fragment is replaced by `•••`, and a keyed HMAC of the full URL is stored beside the snapshot. A restore writes such a URL back only when the link still uses the exact same URL somewhere (destination, fallback, or a routing target), recovered by matching the HMAC; otherwise the restore is refused with a message, and masked values are never written to the link. Changing only a token is still recorded, as a change whose masked values look alike.
- Links created before history existed have no revision. Their first change first appends a `baseline` revision from the system holding the configuration as it was, so that original configuration can be restored.
- Deleting a folder records a `moved` revision for each link it held, in the same transaction, and replacing the password of an already protected link records a value-free `password_changed` entry.
- History belongs to the Short Link: it is kept for the link's lifetime and deleted with the link or its workspace. A deleted member's revisions remain, shown without the member's name.
