# Publish App Associations on workspace domains

An app owner who already sends customers Short URLs on a branded Domain, such as `go.shop.example/spring`, wants those taps to open the installed iOS or Android app instead of a browser tab. iOS Universal Links and Android App Links do this only when the Domain publishes a platform association file and the app declares the Domain. Openlink publishes those files for App Associations: typed, Domain-scoped declarations managed by the Workspace that owns an active Domain. This is not Smart Routing (which picks a Destination URL on the server after a Visit starts) and not deferred deep linking (Openlink cannot carry context through an app install).

## Decisions

- **Domain ownership.** An App Association belongs to exactly one workspace-owned Domain. Only an Owner or Admin of that Workspace can add or remove one, and only while the Domain is active and not disabled. The Default Domain, the application host, and any Domain without a Workspace are shared instance hostnames: they never publish association files and cannot be claimed.
- **App ownership assumptions.** Openlink cannot prove that a Workspace owns an app identifier. Platforms only open an app when both sides agree: the Domain lists the app, and the signed app lists the Domain. Listing someone else's app on your Domain therefore only affects your own Domain. Openlink validates identifier formats; app owners remain responsible for their entitlements, manifests, and signing keys.
- **Generated files only.** Association files are generated from typed fields: iOS App ID prefix (usually the Team ID), bundle ID, and path patterns; Android package name and SHA-256 signing-certificate fingerprints. Openlink never stores or serves user-supplied JSON, custom URL schemes, or URLs. Destination URLs stay HTTP(S) only.
- **Serving and precedence.** `GET /.well-known/apple-app-site-association` and `GET /.well-known/assetlinks.json` are registered before Short URL resolution and answer on every hostname with `application/json`. They never redirect, never fall through to slug resolution, and never record analytics. When the requesting hostname cannot publish, or has no App Association for that platform, the response is a 404.
- **Reserved paths.** `/.well-known/` is never a Short URL path. Every generated iOS entry excludes `/.well-known/*`, `/qr/*`, and `/password/*` before the claimed path patterns, so QR Code scans keep their attribution and password submissions stay on the server. Claimed path patterns cannot start with these prefixes.
- **Path mapping.** iOS path patterns are stored per App Association and published as `components`; iOS 13 or later is required. Android association files cannot scope paths in the supported format, so Android paths are declared by the app's intent filters. Android 15 dynamic App Link components are deferred.
- **Web fallback.** The Web Fallback for an App Association is the Short URL itself. When the app is not installed, the URL is opened in a browser, or the platform declines to open the app, the request reaches Openlink and normal resolution applies: lifecycle rules, password protection, visit limits, and Smart Routing. An app open is not a Visit and does not unlock a Protected Link, because no request reaches Openlink. Apps learn only the Short URL, never the Destination URL. Incoming query parameters are matched by neither file and are never forwarded to Destination URLs.
- **Lifecycle and conflicts.** Hostnames are unique across the instance, so only one Workspace can publish for a Domain. Deleting a Domain deletes its App Associations. Disabling a Domain stops publishing at once. Transferring a Domain to another Workspace deletes its App Associations, so the previous Workspace cannot keep controlling paths on a Domain it no longer owns. The same app appears at most once per Domain and platform. When several iOS apps claim overlapping paths, iOS uses the first match, which is the oldest App Association.
- **Validation is not a device guarantee.** Openlink validates input formats and shows the exact generated files. Whether a device opens the app also depends on the app build, platform caches (Apple fetches through its CDN), the browser, and user choices. Real-device verification steps are documented in `docs/verified-app-links.md`.

## Consequences

Removing an App Association or disabling a Domain changes Openlink's response immediately, but devices and Apple's CDN may keep a cached association for some time. Reverse proxies must forward `/.well-known/apple-app-site-association` and `/.well-known/assetlinks.json` to Openlink over HTTPS without redirects.
