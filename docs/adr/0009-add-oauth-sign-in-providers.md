# Add OAuth sign-in providers

Openlink will add OAuth sign-in with Google and Discord through Laravel Socialite while keeping email and password authentication as a permanent sign-in path. OAuth must not bypass the existing self-hosted security model: provider secrets stay in environment/server configuration, only configured providers are shown in the UI, callbacks run on the canonical application host, and workspace-owned Domains remain redirect-only. Openlink will store external identities in a `social_accounts` table keyed by provider and provider user id, allowing one user to link multiple providers without provider-specific columns on `users`.

OAuth can create accounts, but only under the same registration policy as password registration: the first user may bootstrap the instance and become an Instance Admin, open registration may create users, and invite links may create or join users when still usable. Invite-only or closed registration cannot be bypassed by starting an OAuth flow directly. A provider identity may be linked to an existing user only when the provider returns a verified email matching that user; OAuth creation and linking require verified provider email.

Openlink's own two-factor authentication remains required after OAuth when the account has confirmed 2FA. Accounts created only through OAuth may have a nullable `users.password`; password login must fail cleanly until a password is set, and password reset may establish one later. OAuth scopes stay minimal, access and refresh tokens are not stored, provider names are used only when creating a new user, and provider avatars may be stored on the linked social account without becoming a global user avatar in the first increment.

The first implementation will ship sign-in and registration through OAuth, provider availability detection, invite-link handling, 2FA handoff, rate-limited OAuth routes, feature tests for the security-sensitive branches, and no profile UI for manually linking or unlinking providers. Manual linked-account management can be added later, with the rule that a user must always retain at least one valid sign-in method.
